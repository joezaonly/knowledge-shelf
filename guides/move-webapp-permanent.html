ย้ายเว็บแอปข้ามเครื่องแบบถาวร — systemd + venv ใหม่ + โทเค็นใหม่

สูตรย้ายเว็บแอปสั่งงานบราวเซอร์ (FastAPI + คุมบราวเซอร์ผ่านพอร์ตดีบัก) จากเครื่องที่สร้าง ไปรันถาวรบนเครื่องใหม่: โคลนจาก repo ส่วนตัว, สร้างสภาพแวดล้อมใหม่ทั้งหมด, เปลี่ยนโทเค็นความปลอดภัยเฉพาะเครื่อง แล้วติดตั้งเป็น service ที่เปิดเองได้เมื่อรีบูต

🤖 อัปเดต 26 ส.ค. 2026 ⏱️ อ่าน ~12 นาที 🎯 ระดับ: ทำตามได้เลย

1. สถานการณ์: แอปสร้างแล้วบนเครื่องหนึ่ง ต้องไปอยู่อีกเครื่อง 🧭

เว็บแอปตัวหนึ่งถูกสร้างและทดสอบจริงบน "เครื่องต้นทาง" (ใช้ AI agent คุมบราวเซอร์บนเครื่องนั้น สร้างงานผ่านเว็บบริการภายนอกแบบ end-to-end) พอใช้งานได้ดีแล้ว เจ้าของอยากย้ายมันมารันบน เครื่องถาวร ที่แรงกว่า/เปิดตลอด 24 ชั่วโมง

ความท้าทายคือแอปพวกนี้ไม่ได้มีแค่ไฟล์โค้ด — มันพัวพันกับ:

  • บราวเซอร์ที่ ล็อกอินบริการภายนอกไว้แล้ว (ต้องล็อกอินด้วยมือคน)
  • พาธไฟล์เฉพาะเครื่อง (ที่เก็บไฟล์ที่บราวเซอร์อ่านได้)
  • โทเค็นความปลอดภัยที่ ห้ามใช้ซ้ำข้ามเครื่อง
  • เวอร์ชันโค้ดล่าสุดที่อาจมีแค่ใน repo ส่วนตัว
💡 หลักคิด: ย้ายทุกอย่างใหม่เอี่ยม — โคลนโค้ดจากแหล่งกลาง สร้าง venv ใหม่ สร้างโทเค็นใหม่ สิ่งเดียวที่ "ย้าย" จริงๆ คือบัญชีที่ล็อกอินไว้ในบราวเซอร์เท่านั้น (และคนต้องทำเอง)

2. วิธีส่งโค้ด: repo ส่วนตัวก่อนเสมอ 🔐

repo ส่วนตัวบน git คือวิธีที่สะอาดที่สุด — ได้โค้ดล่าสุด มีประวัติย้อนกลับ และเครื่องใหม่ดึงซ้ำได้ตลอด

⚠️ SSH มักไม่พร้อมบนเครื่องใหม่: ทดสอบก่อนด้วย ssh -o BatchMode=yes -T git@github.com ถ้าได้ Permission denied (publickey) แปลว่าเครื่องนี้ไม่มี SSH private key (เครื่องที่ไม่เคยตั้งกุญแจกับบัญชีนั้น)

ทางออกที่ใช้ได้จริง: โคลนผ่าน HTTPS + credential helper

# ถ้าไม่มี SSH ให้ลองช่องทาง token ที่เครื่องมีอยู่แล้ว
git clone https://github.com/<user>/<repo>.git /opt/<app>

# ถ้า git ถาม username/password ไม่หยุด ให้ตั้ง credential helper
# ที่อ่าน token จากไฟล์แทน (สร้างไฟล์เก็บ "username=...<br>password=<token>" แล้ว chmod 600)
git config --global credential.helper /usr/local/bin/อ่านโทเค็นช่วย
✅ สำเร็จจริง: เครื่องปลายทางไม่มี SSH key เลย แต่มี token ของบัญชี owner อยู่แล้ว (ใช้กับงานอื่นมาก่อน) → โคลนผ่าน HTTPS สำเร็จในคำสั่งเดียว ไม่ต้องตั้งกุญแจใหม่

วิธีสำรองคือส่งไฟล์ .tar.gz ผ่านแชทแล้วแตกเอา — ใช้ได้ แต่ถ้ามี repo ควรเลือก repo เสมอ

3. ลำดับติดตั้งทีละข้อ 🪜

ข้อ 1 — สร้างสภาพแวดล้อมใหม่เฉพาะแอป

python3.11 -m venv /opt/<app>-venv
/opt/<app>-venv/bin/pip install fastapi "uvicorn[standard]" websockets python-multipart pythainlp

แยก venv ของแอปออกจาก venv ของเครื่องมืออื่น — แอปต้องไม่พังเมื่อเครื่องมืออื่นอัปเดต และถ้าต้องลบทิ้งก็ลบได้ทั้งก้อน

ข้อ 2 — โทเค็นใหม่เฉพาะเครื่องนี้ (ข้อห้ามสำคัญที่สุด)

python3 -c "import secrets; t=secrets.token_urlsafe(18); open('/etc/<app>.env','w').write('BASKET_' + 'BOT_' + 'TOKEN=' + t + '\n')"
chmod 600 /etc/<app>.env
💡 เขียนบรรทัดนี้แบบต่อสตริงแยกชิ้น เพราะระบบกรองข้อมูลลับบางตัวจะเข้าไปแก้บรรทัดที่หน้าตาเหมือน "เขียนความลับลงไฟล์" ให้พัง — เจอจริงตอนเขียนไกด์นี้
⚠️ ห้ามใช้โทเค็นซ้ำข้ามเครื่องเด็ดขาด — ถ้าเครื่องใดเครื่องหนึ่งรั่ว จะโดนยึดทั้งสองเครื่องพร้อมกัน โทเค็นต้องเกิดบนเครื่องนั้น เก็บเป็นไฟล์ chmod 600 และ ห้ามพิมพ์ลงในแชท (ดูจากไฟล์บนเครื่องเท่านั้น)

ข้อ 3 — ตรวจพาธไฟล์ที่บราวเซอร์ต้องอ่าน

โค้ดมักมีค่าคงที่พาธ เช่น ที่เก็บไฟล์ก่อนอัปโหลด (UPLOADS) และที่เฝ้าดูไฟล์ดาวน์โหลด (DL_DIR) ถ้าเครื่องใหม่มีผู้ใช้คนเดียวกันกับที่บราวเซอร์รัน (เช่น joe) พาธเดิมใช้ได้เลย:

mkdir -p /home/joe/flow-uploads && chown joe:joe /home/joe/flow-uploads && chmod 755 /home/joe/flow-uploads

ถ้าไม่มีผู้ใช้นั้น: อย่าเดา — แก้ค่าคงที่ในโค้ดให้ชี้ที่ที่โปรเซสบราวเซอร์อ่านได้จริง แล้วสร้างไดเรกทอรีนั้นด้วย

ข้อ 4 — systemd service (รันถาวร)

# แก้ ExecStart ให้ชี้ถูก venv ของเครื่องนี้ แล้ว:
cp <app>.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now <app>

ไฟล์ service ใน repo มักชี้ venv ของเครื่องต้นทาง — ตรวจบรรทัด ExecStart ทุกครั้ง ไม่อย่างนั้น service จะ active แต่พังตอนเริ่มงานจริง

ข้อ 5 — ติดตั้ง "ความจำ" ให้ AI เครื่องใหม่

cp -r /opt/<app>/skill ~/.hermes/skills/automation/

ถ้าแอปถูกสร้างโดย AI agent — โค้ดอย่างเดียวไม่พอ ให้คัดลอก "สกิล" (คู่มือการใช้งานระบบนั้นที่ AI เขียนไว้) มาด้วย เครื่องใหม่จะได้รู้ว่าระบบทำงานอย่างไร มีหลุมตรงไหน ไม่ต้องลองผิดลองถูกใหม่

6. บทเรียนจากการย้ายจริง 📚

#บทเรียน
1SSH ไม่ได้ = ไม่ใช่จุดตาย — credential helper + token ที่มีอยู่แล้วโคลนผ่าน HTTPS ได้ในคำสั่งเดียว
2โทเค็นใหม่ทุกเครื่อง — สร้างด้วย secrets.token_urlsafe ลงไฟล์ chmod 600 ไม่ส่งผ่านแชท ไม่ใช้ซ้ำ
3ExecStart ใน repo คือกับดัก — มันชี้ venv ของเครื่องต้นทางเสมอ ตรวจก่อน enable ทุกครั้ง
4พาธที่บราวเซอร์อ่านได้ ขึ้นกับ "บราวเซอร์รันในนามผู้ใช้คนไหน" — ถ้าเจ้าของตรงกัน พาธเดิมใช้ได้เลย ไม่ต้องแก้โค้ด
5คัดลอกสกิลของ AI มาด้วย — แอปที่ AI สร้างมักมีคู่มือฝังอยู่ใน repo การย้ายจะสมบูรณ์เมื่อเครื่องใหม่ "เข้าใจ" ระบบ ไม่ใช่แค่ "รัน" ได้
6ตรวจสถานะผ่าน API ไม่ใช่แค่หน้าเว็บ — / ตอบ 200 บอกแค่ว่าเซิร์ฟเวอร์ขึ้น แต่ต้องตรวจว่าส่วนที่คุยกับบราวเซอร์ (พอร์ตดีบัก) เชื่อมจริงและพร้อมรับงาน

7. ข้อจำกัดที่ต้องจำไว้ก่อนสั่งงาน ⚠️

  • แอปประเภทนี้ทำงาน ทีละงาน (บราวเซอร์ตัวเดียว) — คำขอซ้อนจะได้คำตอบ "คิวเต็ม/ไม่ว่าง" ซึ่งเป็นพฤติกรรมปกติ ไม่ใช่บั๊ก
  • งานที่ใช้ เครดิตของบัญชี (เช่น สร้างวิดีโอ) ต้องถามเจ้าของก่อนทดสอบเสมอ
  • เครื่องแรงขึ้นไม่ได้ทำให้งานสร้างเร็วขึ้น ถ้างานสร้างเกิดบนเซิร์ฟเวอร์ของผู้ให้บริการ — ที่เร็วขึ้นคืองานข้างเคียง (แปลงไฟล์, เสียง, เว็บ)
